2. WHAT THE FIRMWARE RECORDED - THE KEY EVIDENCE

On the boot following the 17 September crash, the firmware published an
ACPI BERT record. BERT (Boot Error Record Table) is the mechanism by which
the system firmware reports, on the next boot, a hardware error that
occurred during the previous one. It is written by your firmware, not by
Linux.

That record is 92,292 bytes and contains 168 error entries, 71 of which are
marked FATAL. Decoded, the critical entry is:

    Section type : Platform Memory Error
    Severity     : FATAL
    Error type   : 8  (Parity error)
    Location     : Node 0, Card 2, Module 0
    MCA bank     : 0x15 (21)
    MCA_IPID     : 0x0000009600250f00   -> hardware ID 0x96 = Unified
                                           Memory Controller
    MCA_STATUS   : 0xfea000000004080b   -> Valid, Overflow, Uncorrected,
                                           Enabled, MiscV, AddrV, PCC

The last flag is the important one. PCC means "Processor Context Corrupt":
the processor determined its own state could no longer be trusted, which
forces an immediate unrecoverable machine check and a hardware reset. That
is precisely why the machine vanished mid-operation with nothing in the
logs - there was no opportunity for software to record anything.

I would like to pre-empt one likely suggestion: this was not a power cut or
a mains dip. A loss of power cannot write a machine-check status register or
populate an ACPI error record. The processor detected and logged this fault
internally.

Please also note the error TYPE: it is a PARITY error, not a multi-bit ECC
error. Parity is checked on the command/address path between the memory
controller and the modules. Failing memory chips produce ECC errors; a
corrupted command/address path produces parity errors. This is a signal-
integrity fault on the memory interface - which is the same physical failure
mode as the intermittent training failures reported in June, now finally
caught in the act.


3. IT IS NOT A SINGLE FAULTY MODULE

Three independent observations rule that out:

  a) In the same instant, SIX different memory-controller instances logged
     memory error sections (CPER "Card" indices 0, 2, 3, 5, 8, 9 - six of
     the eight channels populated at the time). No single module can cause
     six separate memory controllers to fail simultaneously. This is a
     common-mode fault.

  b) The modules themselves demonstrably work. Whenever the machine is shut
     down and started again by hand - a true cold start - the firmware
     trains all eight channels and reports the full complement (536,189,632
     kB, i.e. ~503 GiB usable). The reduced totals only ever appear after
     the machine has reset itself, when the firmware retrains from a warm
     state. Every module is the correct Kingston part (9965844-002.A01G),
     dual-rank, rated 6400 MT/s, and each is recognised correctly on a cold
     boot.

  c) The six correctable ECC errors are at six unrelated physical addresses.
     A failing memory cell produces repeated errors at the SAME address.

Accordingly I am NOT asking you to replace the memory modules. I do not
believe that is the fault, and swapping them is likely to waste another
round-trip.


4. NEW: CORRECTABLE ECC ERRORS, CONFINED TO ONE CHANNEL

In June I reported that the ECC error counters were clean (ce_count = 0).
They are no longer. Since the 17 September reboot the machine has logged six

Note that the fatal parity error above was on a DIFFERENT controller
